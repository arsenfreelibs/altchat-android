# Резервные каналы доставки сообщений (anti-DPI)

Черновик-брейншторм. Три идеи о том, как доставлять сообщения, когда основной
chatmail-канал (IMAP/SMTP к `alt-to.site`) душится российским DPI.

Контекст и корневой диагноз — в `PROXY_DPI_ISSUE.md`. Там основной путь решения
(Shadowsocks-прокси). Этот документ — про **дополнительные, параллельные** каналы:
не «починить основной», а «продублировать доставку по нескольким путям сразу, чтобы
сообщение прошло хотя бы по одному».

---

## Главный принцип: дублирование безопасно

Всё ниже работает только потому, что у нас есть три «бесплатных» свойства core:

1. **Дедупликация по Message-ID.** Core проверяет `rfc724_mid_exists`
   (`receive_imf.rs:540`): если сообщение с таким Message-ID уже в базе — оно просто
   игнорируется. Значит **одно и то же сообщение можно слать по нескольким каналам
   одновременно** — получатель увидит его ровно один раз, без дублей в чате.
2. **Готовый «приёмник» сырого письма.** `receive_imf(context, rfc724_mid, imf_raw,
   seen)` принимает готовый MIME-блоб и проводит его через весь обычный конвейер
   (расшифровка, привязка к чату, уведомление). То есть любому каналу достаточно
   **доставить тот же самый зашифрованный MIME**, что мы и так шлём через релей, и
   скормить его в `receive_imf`.
3. **Сквозное шифрование уже на уровне MIME.** По всем альтернативным каналам мы гоняем
   **уже зашифрованный** блоб. Промежуточные сервисы (FCM, Яндекс.Диск) видят только
   шифртекст — приватность контента сохраняется.

**Вывод:** не надо изобретать новый формат сообщений. Берём ровно тот MIME, который
core уже формирует для отправки, дублируем его по альтернативному каналу, а на приёме
вызываем `receive_imf`. Дедуп и шифрование достаются бесплатно.

> Требуется в нашем форке core: вынести `receive_imf` в публичный JNI-API
> («инъекция входящего письма») и дать доступ к сырому исходящему MIME из SMTP-очереди.
> Внутренние функции уже есть — нужна только обёртка.

## Идея 1 — параллельно слать/принимать и напрямую, и через прокси

**Проблема, которую решает:** сейчас авто-прокси *переключается* между «напрямую» и
«через прокси» с большими паузами (grace 20 с, 30 с на прокси, recheck 240 с). В
момент переключения сообщения зависают на минуты.

**Идея:** не переключаться, а **гонять оба пути сразу** (happy-eyeballs для всего
транспорта). Кто доставил первым — тот и молодец, дубль отсеётся дедупом.

### Как это могло бы работать
- На отправке: ставим сообщение в очередь и пытаемся отправить **и прямым SMTP, и через
  прокси одновременно**. Первая успешная доставка закрывает спиннер.
- На приёме: держим IMAP-сессию по обоим путям; письмо, пришедшее любым, инъектится
  через `receive_imf`, второй экземпляр отсекается по Message-ID.
- Более лёгкий вариант — racing только на уровне *установки соединения*: для каждого
  IMAP/SMTP-коннекта параллельно пробуем direct и proxy, берём тот, что поднялся первым.

### Плюсы
- Убирает «мёртвые паузы» переключения — нет ожидания grace/recheck.
- Когда DPI душит один путь неравномерно, второй часто проходит.
- Минимальная новая инфраструктура — используем то, что уже есть.

### Минусы / риски
- Core держит **одну** прокси-конфигурацию на аккаунт; честное «оба сразу» требует
  доработки в Rust (racing коннектов в `connect.rs`/`proxy.rs`) — это не чисто
  Android-уровень.
- Двойные соединения = двойной расход (трафик, нагрузка на прокси-пул).
- Если оба пути под DPI (прокси старого типа + прямой) — оба мёртвы, racing не спасёт.
  Работает только когда прокси действительно живой (Shadowsocks).

### Оценка
Средне-высокая сложность (изменения в core). Самостоятельной ценности без рабочего
Shadowsocks-прокси мало — это **ускоритель** поверх Идеи A из `PROXY_DPI_ISSUE.md`, а
не замена ей.

## Идея 2 — дублировать через Cloud Messaging (FCM-пуши)

**Наблюдение:** FCM-пуши в РФ ходят более-менее стабильно (своей замены push-инфра у
РФ пока нет, ломать Google push «целиком» дорого). Приложение уже использует FCM для
уведомлений (`push-token` виден в логах).

**Идея:** использовать пуш как **быстрый резервный канал для коротких сообщений** —
гнать зашифрованный MIME через FCM параллельно с релеем.

### Как это могло бы работать
- FCM — это «сервер → устройство», устройство напрямую другому не пушит. Нужен тонкий
  backend-бридж (у нас уже есть `ALT_API_BASE_URL = api.alt-to.online`):
  1. Отправитель шифрует сообщение (как обычно) и **POST-ит шифртекст** на наш backend.
  2. Backend пушит блоб через FCM на устройство получателя.
  3. Получатель достаёт шифртекст из пуша и инъектит в чат через `receive_imf`.
- Параллельно сообщение идёт и обычным путём через релей — что придёт первым, то и
  показывается; дубль отсекается по Message-ID.

### Плюсы
- **Низкая задержка** для текста — пуш прилетает мгновенно, спиннер закрывается сразу.
- FCM-канал на сегодня в РФ живуч; ломать его «точечно» под нас тяжело.
- Backend видит только шифртекст — контент защищён.
- Точку входа `api.alt-to.online` можно спрятать за CDN/domain-fronting → её самой
  сложнее заблокировать, чем почтовые порты.

### Минусы / риски
- **Лимит размера пуша ~4 КБ** → только короткий текст. Медиа/файлы — мимо (для них
  остаётся релей/прокси). По сути это «быстрая полоса» для текста.
- Нужен **серверный компонент** (приём POST + рассылка через FCM) + интеграция в
  приложение (инъекция входящего).
- Остаётся «первая миля»: POST отправителя на backend должен пройти DPI. Если душат и
  HTTPS к нашему API — нужен тот же CDN/фронтинг, иначе канал тоже под ударом.
- Завязка на Google Play Services / FCM (для foss-сборки без GMS канал недоступен —
  нужен запасной).

### Оценка
Высокая ценность как **низколатентный текстовый fast-path**, средне-высокая сложность
(backend + инъекция в приложение). Хорошо комбинируется с Идеей 3 (текст — через пуш,
тяжёлое — через диск/релей).

## Идея 3 — дублировать через облачное хранилище (Google Drive → Яндекс.Диск)

**Идея:** «мёртвый ящик» поверх облачного диска. Отправитель кладёт файл-сообщение
(тот же зашифрованный MIME) в облако, получатель его оттуда скачивает. Настроить
сначала на Google Drive (удобно конфигурировать не из РФ), затем переключить на
**Яндекс.Диск** — он в РФ заведомо доступен (ломать «свой» Яндекс власти не будут).

### Как это могло бы работать
- Общая или попару-выделенная папка. Отправитель загружает файл, имя кодирует
  получателя + Message-ID; внутри — зашифрованный MIME (как в релее).
- Получатель периодически опрашивает папку, скачивает новые файлы, инъектит через
  `receive_imf`, по Message-ID отсекает то, что уже пришло релеем.
- По сути «IMAP поверх Диска»: то же письмо, другой транспорт. Старые файлы чистим по
  таймеру.

### Плюсы
- **Яндекс.Диск в РФ практически неблокируем** без обрушения самого Яндекса —
  устойчивее любого прокси.
- Дёшево/бесплатно по объёму, тянет и текст, и медиа (в отличие от FCM).
- Google Drive удобен тебе как «настроечный» бэкенд вне РФ, с лёгким переключением.

### Минусы / риски
- **Метаданные утекают провайдеру.** Контент зашифрован, но Яндекс видит: кто, когда,
  как часто, какого объёма обменивается. Для мессенджера в цензурируемом регионе отдавать
  граф общения **российскому** провайдеру — серьёзный компромисс по безопасности. Нужно
  явно проговорить в угрозовой модели (минимум — шифровать/обезличивать имена файлов и
  структуру папок, но трафик-паттерн всё равно виден).
- **Задержка** — это поллинг, не пуш. Без частого опроса доставка «ленивая» (десятки
  секунд–минуты). Частый поллинг = расход батареи/трафика.
- **OAuth и аккаунты:** на каждого пользователя нужен доступ к Диску (свой аккаунт или
  общий сервисный) — это UX-трение и операционная морока (квоты, бан за абьюз,
  очистка).
- Масштабирование общего хранилища, гонки при одновременной записи, уборка мусора.

### Оценка
Высокая устойчивость к блокировке (Яндекс), но высокая сложность и **ощутимый
метаданные-риск**. Кандидат на «канал последней надежды», когда мёртвы и прокси, и
пуш. Не первый приоритет.

---

## Сквозной брейншторм

- **Дедуп — это всё.** Вся затея жива ровно потому, что core отсекает повтор по
  Message-ID. Любой новый канал обязан слать **тот же** MIME с **тем же** Message-ID,
  иначе получим дубли в чате. Это первое, что надо протестировать.
- **Не плодить форматы.** Все каналы возят один и тот же зашифрованный MIME из
  SMTP-очереди и инъектят его через `receive_imf`. Тогда шифрование, привязка к чату,
  уведомления — даром.
- **Расслоение по типу контента.** Текст — в быстрый канал (FCM), медиа/тяжёлое — в
  релей/прокс/диск. Гоняем параллельно, побеждает первый.
- **Первая миля всё равно должна выйти из РФ.** Идеи 2 и 3 ценны тем, что меняют
  заблокированный первый хоп (почта/прокси) на хоп к инфраструктуре, которую РФ не
  трогает (Google push / Яндекс). Идея 1 первую милю не меняет — она лишь умнее
  использует уже имеющиеся (полу-блокируемые) пути.
- **Угрозовая модель.** Контент везде зашифрован, но метаданные — нет. Самый
  чувствительный тут Яндекс.Диск (Идея 3). Это нужно осознанно принять или
  минимизировать.
- **foss-сборка без GMS.** Идея 2 завязана на Google Play Services. Для foss-флавора
  нужен запасной канал (тот же диск или вебсокет к нашему API).
- **Стоимость доставки.** Параллельные каналы = кратный трафик. На прокси-пул и backend
  это ложится нагрузкой — учитывать при масштабировании (см. раздел ёмкости в
  `PROXY_SHADOWSOCKS_SETUP.md`).

## Сравнение

| | Идея 1: direct+proxy параллельно | Идея 2: FCM-пуши | Идея 3: облачный диск |
|---|---|---|---|
| Что меняет | умнее юзает текущие пути | новый быстрый хоп (Google) | новый стойкий хоп (Яндекс) |
| Устойчивость к РФ-блоку | зависит от живого прокси | высокая (пуши ходят) | очень высокая (Яндекс) |
| Задержка | низкая | очень низкая (пуш) | средняя (поллинг) |
| Контент | любой | только короткий текст (~4 КБ) | любой (текст+медиа) |
| Инфраструктура | доработка core | backend-бридж + FCM | хранилище + OAuth |
| Метаданные-риск | нет нового | backend видит трафик | **Яндекс видит граф общения** |
| Сложность | средне-высокая | высокая | высокая |
| Зависимость от GMS | нет | да (нужен fallback) | нет |

## Предлагаемая последовательность

1. **Сначала — рабочий Shadowsocks-прокси** (`PROXY_DPI_ISSUE.md`, вариант A). Это
   фундамент: без живого основного канала резервы — подпорки. Идея 1 включается как
   ускоритель сразу после.
2. **Идея 2 (FCM fast-path)** как первый резервный канал: даёт мгновенную доставку
   текста и закрывает самый болезненный симптом — «спиннер на 30 минут». Требует
   backend, но он логически простой (POST → FCM push).
3. **Идея 3 (Яндекс.Диск)** — «канал последней надежды» для случаев, когда мёртвы и
   прокси, и пуш, и для медиа. Внедрять осознанно, с учётом метаданные-риска.

Общая логика: **один зашифрованный MIME — много труб — дедуп на приёме.** Чем больше
независимых труб, тем выше шанс, что сообщение пройдёт хотя бы по одной.
